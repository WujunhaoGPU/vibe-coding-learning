# Harper Reed — My LLM Codegen Workflow：中文学习版

> 本文是学习导读与结构化摘要，不是逐字翻译。涉及作者具体措辞、提示词与细节时，请回到原文核对。

## 一句话理解

Harper Reed 的核心不是“找到一个更好的 Prompt”，而是把 AI 编程拆成几个彼此分离的循环：**先把想法讨论清楚并形成 spec，再把 spec 转化成可执行计划，最后才让代码模型按小步骤实现。**

## 1. 为什么不能直接从想法跳到代码

一个模糊想法里通常藏着大量没有被说出来的选择：用户是谁、什么算完成、哪些功能暂时不要、数据怎么流动、错误怎么处理、哪些技术选择其实还没决定。

如果直接让模型开始写代码，这些空白不会消失，模型只会替你补完它们。于是很容易出现“人只决定了一部分，AI 自动补完其余部分，然后很快得到一个完整实现”的情况，但那些补完的决定未必是你真正想要的。

## 2. Brainstorm → Spec

第一步不是编码，而是让模型像需求访谈者一样持续追问，一次只处理一个问题。重点不是某个固定提示词，而是：不让模型一次性脑补完整需求；通过连续问答逼出隐藏决策；最终把讨论沉淀成稳定的文本 artifact，例如 `spec.md`。

`spec.md` 的价值在于它可以被重新审阅、发现矛盾、交给其他模型，并作为后续计划的固定输入。聊天上下文是流动的，文件则能把关键决定变成工程资产。

## 3. Spec → Plan

有了需求说明之后，不是立刻生成代码，而是进一步回答：按什么顺序实现、每一步依赖什么、如何拆成小增量、什么时候验证、哪些步骤不应同时推进。

最终可以形成类似 `prompt_plan.md` 和 `todo.md` 的文件，把“我要造什么”继续转成“我准备怎样一点点造出来”。

## 4. 小步 Implementation

真正编码时采用小循环：取一个小任务 → 实现 → 验证 → 更新 todo → 再取下一个任务。

这样可以降低长上下文漂移、一次改动过大、难以 review、问题来源不清和跨会话状态丢失等风险。`todo.md` 不只是清单，也是一种跨模型、跨会话保存状态的方法。

## 5. Greenfield 与已有项目

这套方法对从零开始的项目尤其自然。但已有项目还有一个额外事实来源：现有代码本身。因此 brownfield 场景通常需要在写 spec 之前加入“理解当前系统、已有行为与约束”这一步。

## 6. 真正值得学的四点

1. 把需求澄清、架构思考、任务拆分、代码实现这些不同性质的认知任务分开。
2. 让错误尽可能早暴露；需求阶段改一句话，比写完几千行代码再返工便宜得多。
3. 使用持久 artifact 对抗上下文漂移。
4. AI 的速度会放大方向错误，所以“方向错了”比“代码写得慢”更贵。

## 7. 读完后请自己回答

1. 为什么直接 idea → code 容易出问题？
2. `spec.md` 和 `prompt_plan.md` 分别解决什么问题？
3. 为什么 todo/checklist 对 AI agent 特别有价值？
4. 如果模型能力比 2025 年强很多，这套流程哪些部分仍然有价值？
5. 哪些部分可能只是当时模型能力有限造成的 workaround？

## 8. 迁移题

回想最近一次返工：它是因为“代码写错”，还是因为“开始写之前就没有真正决定清楚”？如果是后者，再判断缺的是 spec、架构候选方案、对现有系统的理解，还是一个必须停下来让人确认的 decision gate。
